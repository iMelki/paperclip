## Concrete blocker and source repair

The stock install route immediately called lifecycle.load; a normal upgrade
immediately reactivated the replacement. The GitHub plugin declares a minute job.
When repository mappings are configured, its scheduled path can reach repository
sync and queued agent wakeups. This is a real producer path, not evidence that a
current live job already ran. An intended plugin worker is not an AI provider run.

This narrow private delta adds optional `activate: false` to the existing install
and upgrade APIs. Install retains the installed row without calling lifecycle.load.
Upgrade reuses the existing package loader/path persistence and UUID, saves
upgrade_pending before unloading, and requires the configured runtime unload seam.
Unload or replacement failure remains held rather than silently reactivating.
A separate existing enable action now also accepts installed packages. Requests
that omit the option retain their original immediate activation behavior.

Independent review requested a correction: a rejected installed enable could
remain saved ready if the loader's own markError first encountered a failed
runtime unload. The successor now reads back after activation failure and, if
still ready, persists error without depending on another successful unload.
Thrown activation, returned failure, and failed-cleanup-returned-failure cases
are authored. These are UNRUN; this repair does not prove failed workers drained,
and database/readback failure still cannot be represented as verified held state.

Local upgrade paths use the existing canonicalizer and managed bundled-source
floor before lifecycle mutation. Nonboolean activation and malformed paths fail
validation. UI API types expose the option without a new component/library.
The current loader already retains packagePath and job reconciliation already
retains paused rows; those fixes were reused, not duplicated.

This is NOT a distributed activation lock or native process-drain proof. Existing
enable/configuration/file-watch producers still require single-owner maintenance
custody and installed configuration readback. A lost hold fails readback but does
not establish that a concurrent actor never activated. Installation may validate
packages/apply schema migrations; dormant means no requested runtime activation,
not no filesystem/database work. No runtime installation or activation occurred.
